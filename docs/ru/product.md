# Findrail: продукт, архитектура и развитие

## Одним абзацем

Findrail — открытый поисковик по твоим данным: выбираешь папки и подключаешь
нужные источники, а затем находишь документы, заметки и обсуждения через одно
поле поиска. Каждый результат показывает подходящий фрагмент, источник и адрес
оригинала. Базовый поиск работает локально без AI-подписки; семантический поиск,
коннекторы и клиенты расширяют общее ядро. Сейчас реализован поиск по локальному
тексту, Markdown, коду и текстовым PDF, предпросмотр и автообновление;
подключение сервисов входит в план.

## Задача пользователя

«Я помню, что уже видел это объяснение, но не помню, в какой заметке, файле или
обсуждении». Пользователю нужно вернуть конкретный источник и нужное место в
нём. Это определяет порядок развития: качество найденных фрагментов, простая
установка, понятная свежесть индекса, затем расширение числа источников.

Первый сегмент — разработчики и люди с большими коллекциями заметок. У них
много текстовых данных и повторяющиеся поисковые задачи. Следующие сегменты —
исследователи и пользователи собственного хостинга. Это гипотезы для проверки;
командная платформа требует отдельной работы с доступами.

## К чему должен прийти продукт

| Сценарий | Поведение готового продукта | Сейчас |
|---|---|---|
| Найти объяснение в заметках | Фрагмент, источник, просмотр и переход к оригиналу | Поиск, просмотр и копирование адреса |
| Вспомнить решение по проекту | Общая выдача по локальным документам и GitHub | Только локальные файлы |
| Найти место в PDF | Текст, номер страницы и предпросмотр | Реализовано для текстовых PDF |
| Получить актуальную выдачу | Фоновая синхронизация и видимые ошибки | Ручной повтор индексации |
| Искать по смыслу | Необязательная модель и ссылки на исходные фрагменты | Запланировано |
| Передать контекст AI-инструменту | Read-only MCP с ограниченными источниками | Запланировано |

## Позиционирование

В этой области уже существуют [Khoj](https://github.com/khoj-ai/khoj) и
[Onyx](https://github.com/onyx-dot-app/onyx), предлагающие AI-интерфейсы к
информации. Поэтому широкая формулировка «поиск по всем данным с AI» сама по
себе не даёт преимущества. Наша продуктовая гипотеза — компактное локальное
приложение, которое полезно без модели, легко установить и которое постоянно
показывает исходный материал. Сравнивать надо на одинаковых задачах поиска и
данных; утверждений о превосходстве по скорости или качеству пока нет.

## Архитектура для большого проекта

Первый процесс содержит самостоятельные модули. Они позволяют добавлять
возможности без обязательной установки нескольких сервисов.

| Модуль | Ответственность |
|---|---|
| `cmd/findrail` | Запуск и завершение процесса |
| `internal/connectors` | Чтение явно выбранных источников |
| `internal/extract` | Ограниченное по ресурсам извлечение текста |
| `internal/ingest` | Атомарное обновление индекса |
| `internal/store/sqlite` | Документы, источники, FTS и миграции |
| `internal/search` | Контракт запросов и результатов |
| `internal/sync` | Будущие задачи, наблюдение и повторные попытки |
| `internal/semantic` | Будущие чанки и необязательные embeddings |
| `internal/transport` | HTTP сейчас, MCP позже |
| `pkg/connector` | Экспериментальный контракт расширения |
| `web` | Развитие клиентского интерфейса |
| `api`, `docs`, `scripts`, `test` | API, решения, инструменты и проверки |

Структура следует выбранным соглашениям
[project-layout](https://github.com/golang-standards/project-layout).
Это соглашения сообщества, а не обязательный стандарт команды Go. Будущие
модули содержат дизайн и критерии реализации. Рабочее ядро уже индексирует,
ищет и отдаёт результаты через CLI и локальный HTTP.

## Порядок развития

1. Проверить локальную альфу с пользователями: PDF, наблюдение за файлами, просмотр фрагментов,
   качественная выдача, установка и работа на трёх ОС.
2. Добавить GitHub: явный выбор репозиториев, read-only доступ, лимиты API,
   история синхронизации и корректное удаление документов.
3. Стабилизировать SDK: версии контрактов, пример адаптера и набор проверок
   для независимых контрибьюторов.
4. Добавить необязательный семантический поиск после оценки его пользы.
5. Выпустить desktop launcher, MCP и интеграции с редакторами.
6. Развивать командное использование и управляемый хостинг после проверки
   спроса и реализации авторизации.

Подробные задачи и условия готовности находятся в
[implementation plan](../implementation-plan.md), этапы — в
[roadmap](../roadmap.md). Сроки и число контрибьюторов пока не обещаем.

## Как получить пользователей и звёзды

Для запуска нужен понятный демонстрационный сценарий: найти потерянный фрагмент
в нескольких источниках и перейти к оригиналу. Сначала 10–15 независимых
пользователей проверяют установку и реальные задачи поиска. Затем публикуем
короткое демо, воспроизводимые измерения и задачи для первых контрибьюторов.
Коннекторы и форматы дают сообществу конкретные направления для участия.

Смотреть следует на успешные поиски, повторное использование и независимые
вклады. Звёзды отражают интерес, но не доказывают качество или доход. В текущем
приложении нет аналитики; участие в исследованиях добровольное. Публикации,
рассылки и обращения к людям требуют отдельного поручения.

## Открытость и экономика

Ядро, локальные клиенты и интерфейсы расширения — Apache-2.0. Возможные источники
дохода: поддержка, спонсорство и управляемая инфраструктура для тех, кто хочет
хостинг. Локальный продукт должен оставаться самостоятельным. Это направления
проверки бизнеса; обещания дохода или «гарантированного миллиона» нет.

## Границы текущей версии

Индекс содержит исходный текст и пути в незашифрованной SQLite-базе. HTTP слушает
только loopback. Выбранные папки читаются без изменения оригиналов, скрытые
файлы и ссылки пропускаются, размер чтения ограничен. Фильтр имён не способен
найти все секреты внутри обычных документов. Повторный полный обход обновляет
изменения и удаляет исчезнувшие документы; ошибка отменяет всю транзакцию.

Рабочие команды и запуск интерфейса есть в [кратком руководстве](overview.md).
